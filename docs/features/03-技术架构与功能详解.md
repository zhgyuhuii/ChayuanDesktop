# 察元 Chayuan · 技术架构与功能详解(开发/运维向)

> 面向开发与运维:每个功能讲清**所属模块 · 关键接口 · 数据流 · 实现要点**。
> 三大代码库:`chayuan`(WPS 加载项,JS/Vue)、`chayuan-server`(FastAPI/Python)、`chayuan-client`(TS/React,pnpm workspace)。三者是一个端到端系统。

---

## 〇、总体架构

```
WPS 加载项 / Web / Desktop 客户端
        │  选知识源(ku_ids)、发对话、要产物
        ▼
chayuan-server(FastAPI)
  api_server(协议适配/鉴权/参数校验)
        │
        ├─ kb_query.service ── retrieval.query.orchestrator
        │        refs → authz → router → adapters → results
        ├─ agent / tools_factory(Text2SQL、搜索、生成…)
        ├─ multimodal(ASR/TTS/视频/图像 → artifacts)
        ├─ model gateway(本地 sidecar + 云端厂商)
        └─ storage(local / minio)+ /v1/files 统一文件端点
        ▼
PostgreSQL(业务库)· Redis(缓存)· Milvus(向量)· MinIO(对象存储)
```

### 核心架构原则(贯穿全系统)
1. **统一知识查询路径**:`ku_ids` / `KnowledgeRef` 是知识源选择的唯一真源——`doc:<kb>`、`src:<source_id>`、`office:<owner>[:group]`。优先 `POST /api/v1/kb-query/search`,旧接口(`/knowledge_base/search_batch` 等)仅作兼容层。
2. **Query Engine 分层(路由无关)**:`API route → kb_query.service → retrieval.query.orchestrator → refs/authz/router/adapters/results`。路由文件只做协议适配,不堆业务分发。
3. **结构化数据 ≠ 文档 RAG**:聚合类问题走 `intent → schema linking → SQL planning → 只读 AST 校验 → 执行 → 结果校验 → grounded answer`,不退化成 chunk 检索。
4. **向量源 ≠ 文档附件**:外部向量库返回 collection/vector id/payload/metadata/score,UI 区分 `document/structured/vector/office`,下载按钮仅对文档来源开放。
5. **查询端不可覆盖 embedding 模型**:查询模型跟随 KB 索引配置。

## 一、知识查询与检索(retrieval / kb_query)

| 子能力 | 模块/路径 | 接口 | 数据流 / 要点 |
|---|---|---|---|
| 统一查询入口 | `kb_query/service.py`、`kb_query/schemas.py` | `POST /api/v1/kb-query/search` | 解析 `ku_ids` → 编排 → 返回 `QueryBlock/RetrievalHit/Citation/Diagnostic` |
| 引用解析 | `retrieval/query/refs` | — | 解析 `doc:* / src:* / office:*` 为内部 source 句柄 |
| 权限判定 | `retrieval/query/authz` | — | 用户/应用/游客统一鉴权,KB/源/文档多粒度 RBAC |
| 路由 | `retrieval/query/router` | — | 识别 `document_qa / structured_aggregate / structured_lookup / vector_semantic / multi_source` |
| 编排 | `retrieval/query/orchestrator` | — | 并发、超时、错误隔离、trace、结果聚合 |
| 适配器 | `retrieval/query/adapters/{document,structured,vector,office}.py` | — | 按源类型实现检索;结构化带 SQL/表/行诊断,向量带 collection/vector id/metadata |
| 高级索引 | RAPTOR / GraphRAG | — | 文档分层摘要树(RAPTOR,chunk>阈值按文件构树)、图谱索引 |
| 全文总结 | `kb_summary` + `kb_summary_api` | `/kb_summary_api/summarize_file_now` | 取全文 `list_docs` → 内容哈希缓存 → 超阈 needs_confirm → SummaryAdapter map-reduce → 回写摘要 FAISS;**注意按 n_ctx 预算化防 context 溢出** |

**客户端侧**:WPS 端有 T1–T4 四层查询规划(`src/services/kb/queryPlanner.js` 切分→`clusterer.js` 本地聚类→`localDistiller.js` LLM 蒸馏→`searchOrchestrator.js` 批查去重评分);React 端 `features/kb/` 走 `KbAskComposer` → `KbResultBlock`。

## 二、结构化数据(knowledge_source/sql + agent)

| 子能力 | 模块/路径 | 要点 |
|---|---|---|
| Text2SQL | `agent/tools_factory/text2sql.py`、`retrieval/query/adapters/structured.py`、`structured_tools.py` | schema linking → SQL planning → 只读 AST 校验 → 执行 → 结果校验;17 种 SQL 方言 |
| 数据源 connector | `knowledge_source/sql/`(+ MongoDB/ES) | 表/列白名单或 schema cache;数据挂载物化 |
| 前端 | `features/kb/detail/StructuredKbDetail.tsx` | 行级结果表格;显示 SQL + 诊断 |

**红线**:SQL 只读;聚合意图必须校验 SQL shape;执行失败返回可诊断错误,不让 LLM 编答案。

## 十二、关键技术红线(开发须知)

1. 路由文件不堆业务 dispatch;业务在 service/orchestrator。
2. 结构化问题不走文档检索兜底后让模型乱答。
3. 前端必须保存 `ku_id/kind`,不能只存显示名。
4. vector/source 结果不显示成可下载文档附件。
5. 查询阶段不接受外部 embedding model 参数。
6. 访问 KB/source 必须先鉴权。
7. 未验证不提交/推送代码。
