# 实时数字人 + 百万并发 架构设计

> 日期:2026-06-05
> 状态:设计稿(待评审)
> 背景:在线数字人当前"说一句停很久、不连贯",根因是技术路线选错(服务端逐帧 wav2lip),
> 架构上注定撑不了实时 + 高并发。本文给出能撑到百万并发的目标架构、技术选型与分阶段落地路线。

---

## 1. 问题陈述

### 1.1 现状
- 在线对话:大模型 SSE 流式出文字 → 按句切 → 每句 `/say` 在**服务端逐帧跑 wav2lip** 生成口型片段 → 浏览器队列播放。
- CPU 单机:wav2lip 一句话(100+ 帧)要数秒;队列预取追不上播放 → **句间长停顿**。
- 无推理服务化、无批处理、无队列、无横向扩展 → **单机一次基本只能服务一路**。

### 1.2 根本矛盾(必须先认清)
在 **CPU 单机 + 逐帧神经渲染(wav2lip)** 这个组合下:
- **真口型(逐帧渲染)= 慢** ↔ **连贯(跟得上语音)= 快**,二者不可兼得。
- 这不是"压榨 CPU"能解决的;是**技术路线**问题:逐帧神经渲染是离线/小规模路线,不是实时/高并发路线。

### 1.3 目标
1. **说话连贯**:语音随大模型输出快速、连续合成播放,口型与语音基本一致。
2. **高并发**:几百万人同时在线问同一个/不同数字人,系统稳定、低延迟、成本可控。

---

## 2. 业界主流技术路线

| 路线 | 代表产品/项目 | 实时性 | 并发友好度 | 说明 |
|---|---|---|---|---|
| **音频→口型参数(blendshape/viseme)+ 端侧渲染** | NVIDIA Audio2Face、HeyGen、D-ID、Synthesia | 参数毫秒级,渲染在端 | ⭐⭐⭐⭐⭐ | 服务端只算轻参数,渲染下放浏览器 WebGL → 服务端零渲染压力 |
| **流式 TTS + 流式驱动** | CosyVoice、GPT-SoVITS、edge streaming | 首包 <300ms | ⭐⭐⭐⭐ | 边出文字边出音频,语音先连贯 |
| **神经渲染实时优化** | MuseTalk、GeneFace++、ER-NeRF | GPU 30fps | ⭐⭐ | 每路占 GPU,靠 GPU 池扩展 |
| **逐帧 GAN(当前这套)** | wav2lip、SadTalker | 离线/慢 | ⭐ | 撑不住实时/高并发 |

**核心洞察**:百万级实时数字人(HeyGen Interactive Avatar、D-ID Agents、Soul Machines)的共同点是
**「音频 → 口型参数 → 渲染下放客户端」+「推理服务动态批处理」**,服务端**绝不逐帧生成视频**。

## 3. 目标架构(可撑百万并发)

```
┌─────────────────────────── 客户端(浏览器 / App) ───────────────────────────┐
│  - 一次下载 avatar 资产(2D 分层 PSD / 3D glTF + 贴图)经 CDN                  │
│  - 运行时:WebGL/Three.js 本地渲染口型(收口型参数流驱动)                     │
│  - 播放流式音频(WebAudio);收文本流显示字幕                                 │
│  - 仅消耗:文本流 + 音频流 + 口型参数流(带宽极小,KB/s 级)                  │
└───────────────▲ WebRTC / WebSocket(边缘 SFU 就近接入)──────────────────────┘
                │
┌───────────────┴────────── 无状态接入层(k8s + HPA,水平扩展)──────────────┐
│  鉴权 / 限流 / 会话路由 / SSE·WS 网关                                        │
└───────┬──────────────────┬───────────────────┬──────────────────┬──────────┘
        │                  │                   │                  │
   ┌────▼─────┐      ┌─────▼──────┐      ┌─────▼───────┐    ┌─────▼─────┐
   │ LLM 推理 │      │ 流式 TTS   │      │ 音频→口型   │    │ 缓存层    │
   │ vLLM/TGI │      │ 集群       │      │ blendshape  │    │ Redis     │
   │ continuous│     │ CosyVoice/ │      │ 轻量模型    │    │ 相同/相似 │
   │ batching │      │ GPT-SoVITS │      │(可 CPU)    │    │ 问答+音频 │
   │ +KV cache│      │ 动态批处理 │      │ 动态批处理  │    │ 缓存      │
   └────┬─────┘      └─────┬──────┘      └─────┬───────┘    └───────────┘
        └──────────────────┴───────────────────┘
                           │  推理统一走 GPU 池
        ┌──────────────────▼───────────────────────────────┐
        │  GPU 推理池:Triton / Ray Serve 动态 batching       │
        │  KEDA 按"队列长度/GPU 利用率"自动扩缩                │
        │  模型 fp16/int8 + TensorRT/ONNX                     │
        └────────────────────────────────────────────────────┘
        消息队列 Kafka / Redis Stream(削峰填谷) | 对象存储 + CDN(avatar 资产)
```

### 3.1 撑百万的三大支柱
1. **推理动态批处理**:把多用户请求合批,一次 GPU 前向服务一批人 → GPU 利用率拉满(LLM 用 continuous batching,TTS/口型用动态 batching)。
2. **渲染下放客户端**:服务端只算"口型参数"(每帧几十个 float),浏览器 WebGL 渲染 → 服务端压力与人数解耦。
3. **缓存 + 队列 + 自动扩缩**:同一数字人海量重复问题 → 回答/音频缓存命中率高;队列削峰;KEDA 按负载扩缩 GPU。

## 4. 组件技术选型

| 组件 | 推荐 | 备选 | 理由 |
|---|---|---|---|
| LLM 推理 | **vLLM**(continuous batching, PagedAttention) | TGI, SGLang | 高吞吐、KV cache 共享,百万并发性价比最高 |
| 流式 TTS | **CosyVoice2 / GPT-SoVITS(流式)** | edge-tts(轻量兜底)、商用(火山/Azure) | 首包低延迟、可克隆音色、可自部署批处理 |
| 音频→口型 | **Audio2Face 类 audio2blendshape 小模型** | wav2lip(仅高质量离线档) | 轻量、可 CPU 实时、参数化、批处理友好 |
| 端侧渲染 | **Three.js / PixiJS + Live2D/VRM/glTF** | Unity WebGL | 渲染下放,服务端零渲染 |
| 实时传输 | **WebRTC(媒体)+ WebSocket(参数/文本)** | SSE(单向兜底) | 低延迟、边缘 SFU 就近 |
| 推理网关 | **Triton Inference Server / Ray Serve** | KServe | 动态 batching、多模型编排 |
| 编排/扩缩 | **k8s + HPA + KEDA** | — | 按 GPU 队列长度扩缩 |
| 队列 | **Kafka / Redis Stream** | NATS | 削峰、异步 |
| 缓存 | **Redis**(回答/音频/参数) | — | 同一数字人重复问题命中率高 |
| 存储/分发 | **对象存储(S3/MinIO)+ CDN** | — | avatar 资产一次下发、就近 |

## 5. 分阶段落地路线

### 阶段 0 — 单机 CPU(现在):先把"语音连贯"做出来
- **语音与口型解耦**:大模型边出文字边**流式 TTS**(首包就播,句句连续,不等渲染)。
- 口型在 CPU 上退到**轻量近似**(viseme/振幅驱动 2D 口型),或干脆只语音 + idle。
- **不再在 CPU 上逐句跑 wav2lip**(那正是停顿源)。
- 产出:声音连贯、低延迟;口型近似。**这是单机 CPU 能拿到的最佳体感**。

### 阶段 1 — 单机/少量 GPU:真口型 + 连贯
- 口型换 **MuseTalk(GPU 实时 30fps)** 或 audio2blendshape;TTS 流式。
- 单机能稳定服务数路~数十路实时对话。

### 阶段 2 — 规模化(百万并发):换路线 + 服务化
- 口型路线切到 **audio2blendshape + 端侧 WebGL 渲染**(服务端不再出视频)。
- 推理服务化:LLM(vLLM)+ 流式 TTS 集群 + 口型参数服务,统一 **Triton/Ray 动态批处理**。
- 客户端:一次下 avatar 模型;运行时只收 文本流 + 音频流 + 口型参数流。
- 基础设施:Kafka 削峰、Redis 缓存、CDN 分发、k8s + KEDA 按 GPU 负载扩缩、WebRTC 边缘 SFU。
- 降本:模型 int8/fp16 + TensorRT;相似问题去重缓存;冷热分离。

## 6. 容量与成本(量级估算,需实测校准)
- **渲染下放客户端后**,服务端每路实时对话的服务端成本主要是:LLM token + TTS 音频 + 口型参数(极小)。
- 动态批处理下,单张 A10/L4 可同时服务数十~上百路口型参数/TTS(参数化模型很轻)。
- 百万**同时在线**≠ 百万**同时说话**:真正占算力的是"正在生成回答/语音"的并发,通常是在线数的几 % → 靠队列 + 自动扩缩 + 缓存把峰值摊平。
- 缓存:同一数字人(如客服/带货)Top 问题高度集中,回答 + 音频缓存命中率可达很高 → 直接砍掉大头算力。

---

## 7. 从当前代码迁移
- 当前 `/say`(服务端逐帧 wav2lip)在阶段 0 改为:**默认流式 TTS 连贯播音**(口型近似),wav2lip 仅保留为"GPU 高质量档"。
- `digital_human_public_routes`(公开页)与生成管线解耦:公开页走"实时轻量路线",生成管线(`jobs`)保留"离线高质量逐帧"路线(出可下载成片用)。两条路线分明,不再混用。
- 阶段 2 把公开页前端换成 WebGL 渲染器,服务端 `/say` 改为推**音频 + 口型参数**而非视频。

---

## 8. 待决策 / 风险
1. **口型质量 vs 实时**:阶段 0 口型只能近似;要真口型必须 GPU。需用户接受这个边界。
2. **avatar 资产形态**:端侧渲染需要 avatar 是**可驱动模型**(Live2D/VRM/3D 或 2D 分层),而非一张静态图。这要改"形象"的制作方式(从一张照片 → 一个可驱动 avatar),是阶段 2 的前置。
3. **自部署 vs 商用**:流式 TTS、口型模型可自部署(可控、可克隆)或接商用(省事、按量计费)。规模化时成本模型不同。
4. **本项目定位**:若主要是**桌面单机**,阶段 0/1 足够;若要做**SaaS 百万并发**,需阶段 2 的多机 GPU 集群投入。两者架构差异巨大,需先明确定位再投入。

---

## 9. 结论
- 当前"服务端逐帧 wav2lip"**架构上撑不了实时 + 百万并发**,不是调参能解决。
- 正解是 **「音频→口型参数 + 端侧渲染」+「推理服务动态批处理」+「缓存/队列/CDN/自动扩缩」**。
- **立即可做(单机 CPU)**:流式 TTS 让语音先连贯(语音/口型解耦),口型退近似。这是收益最大、风险最小的第一步。
- 规模化是 GPU 多机 + 换渲染路线 + 改 avatar 形态的大工程,需先定产品定位(桌面 vs SaaS)。
