# 对话历史完整还原 — Design

日期: 2026-06-25
范围: chayuan-client(前端会话还原) + chayuan-server(会话配置漫游)
目标: 点击历史对话,**完整还原对话状态**——消息上下文 + 当时选中的知识库 + 模型 + 高级参数
      + 反馈,并能基于上下文继续提问;支持跨设备漫游。本期聚焦**对话流**(普通chat/知识
      问答/智能体/技能);视频生成/数字人/图像是独立任务页,后续单独评估。

## 背景与现状(调研结论)

**能还原**:消息历史(listMessages)+ 基本会话信息(id/title/model字符串/mode/时间)。

**还原不了(缺口)**:
1. composer 全部状态:选中知识库(selectedKuIds/selectedKbs)、模型(modelId/platformName)、
   检索模式(searchMode)、深度思考(deepThink)、高级参数(temperature/topK/scoreThreshold/
   rewriteStrategy/embedModelId/selectedTools/selectedMcps/promptName)——**全部丢失**。
2. 反馈(点赞/点踩):只发 Langfuse,本地 messages 无字段,重开不回显。
3. 服务端 ConversationModel 极简(id/name/chat_type/user_id/create_time),不记 model/KB/参数
   → 不能跨设备漫游。

**关键**:`ConversationRecord.meta`(JSON 列)**已预留但全是 null、没人写**——还原状态的天然载体。
composer 是 per-lane scoped store(useComposerS)+ partialize/seed 机制(现成的恢复入口)。

## 决策(已逐节确认)

方案1:**会话携带「配置快照」,本地 meta 即时还原 + 服务端漫游镜像**。参考主流系统
(ChatGPT/Claude/Gemini):一个会话 = 消息历史 + 一份「会话配置快照」,点开同时恢复上下文与设置。

## 1. 数据模型

会话配置快照(对话流通用,一份即可,用 mode 区分类型):
```ts
interface ConvConfigSnapshot {
  modelId?: string; platformName?: string;
  mode?: 'plain' | 'kb' | 'agent' | 'skill';
  selectedKuIds?: string[];   // 统一KB真源(doc:/src:/office:)
  selectedKbs?: string[];     // 旧文档KB兼容镜像
  selectedTools?: string[]; selectedMcps?: string[];
  deepThink?: boolean;
  searchMode?: 'precise' | 'balanced' | 'fast';
  rewriteStrategy?: string; embedModelId?: string;
  temperature?: number; maxTokens?: number;
  topK?: number; scoreThreshold?: number; promptName?: string;
}
```
存放:
- **本地**:写进已预留的 `ConversationRecord.meta`(JSON 列,SQLite/Dexie 都有)——零 schema 改动。
- **服务端**:`ConversationModel` 加结构化字段(见 §4)。

反馈:本地 `ChatMessage` 加 `feedback?: 1 | -1 | null`(随消息 `parts` JSON 存,persistence 现成)。
回显按消息读。为什么一份通用快照:对话流共用同一 composer,字段同一套,YAGNI。

## 2. 写入时机(持久化)

- **配置快照**:在 `ConversationView` 已有落库点(发消息后/流式结束 `upsertConversation`,
  约 186-223 行)追加 `meta = snapshotFromComposer(composer.getState())`——每次发消息把当前
  composer 快照随会话写进 `meta`。低频,无需额外 debounce;`meta` 始终反映最近一次发消息时
  的设置。首条消息建会话写初值,后续每次更新(中途改 KB/模型也跟上)。
- **反馈**:`MessageBubble.submitFeedback` 现只发 Langfuse,追加 `updateMessage(messageId,
  {feedback})` 写本地库 + 服务端镜像(§4)。
- **服务端镜像**:发消息落库时同步 PATCH 服务端会话 `config_snapshot`(best-effort,失败仅
  警告,本地 `meta` 为即时真源)。

## 3. 读取(还原)

点历史对话(`ConversationView` 监听 `activeId` 变化处扩展):
1. `getConversation(id)` 读 `meta`(本地优先,缺则拉服务端 §4)。
2. `applySnapshotToComposer(scopedStore, meta)` seed 进当前对话 lane 的 scoped composer store:
   恢复 modelId/platformName/mode/selectedKuIds/selectedKbs/tools/mcps/deepThink/searchMode/参数。
3. `listMessages(id)` 恢复消息(现有);每条 `feedback` → MessageBubble 初始点赞点踩从
   `message.feedback` 读(不再恒空)。

顺序:先 seed composer(知识库/模型/参数就位)再渲染 messages → KB 来源条、模型 pill 立即正确。
兜底:草稿态/无 meta → composer 默认(现状不变);meta 缺字段 → 该字段默认;恢复 selectedKuIds
(绑了KB)→ 模型选择器按既有逻辑收窄 chat/vl(正确,还原了「当时绑着KB」)。

## 4. 服务端漫游(跨设备)

`ConversationModel` 扩展(向后兼容,nullable):
- 加 `config_snapshot`(Text/JSON,存整份 ConvConfigSnapshot)——一列搞定,字段演进无需再迁移。
- 可选 `model_id`(String 单列,便于后台列表展示)。
- Alembic 迁移 `ADD COLUMN ... NULL`,旧行 NULL(点开按草稿默认兜底)。

同步:
- 写:发消息落库时 PATCH 服务端会话 `config_snapshot`(best-effort)。
- 读:点历史对话本地有 `meta` 直接用;本地缺(换设备/浏览器)→ GET 服务端 `config_snapshot` → seed。

反馈漫游:本次会话配置漫游为核心。反馈先落本地(§2)。服务端镜像取决于服务端 message 表——
实现时确认:有 message 模型就加 `feedback` 列同步;无则反馈本次只本地、漫游列为后续。不阻塞主目标。

## 5. 上下文继续

- 现状 `buildChatRequest` 已把 `messages.slice(0,-1)` 作 history + 塞 `conversation_id`
  (ConversationView:47)——逻辑本就对。
- 补缺口:点历史对话后 `activeId`=该会话 id、恢复 messages 进 chat 状态 → 继续发消息时
  history 含恢复的上下文 + `conversation_id` 指向该会话 → 后端 `/chat/v2/chat`(ChatGraph)
  基于上下文续答。核对历史会话(非草稿)下 `conversation_id` 被后端正确认(必要时续答消息
  带齐 history 让后端可重建上下文)。

## 测试

- 纯函数 vitest:`snapshotFromComposer`/`applySnapshotToComposer` **往返一致**(不丢字段)、
  `meta` 序列化/反序列化、缺字段兜底默认。
- 服务端:`config_snapshot` 读写 + alembic 迁移(旧行 NULL 不炸)。
- 反馈本地存/回显往返。

## 分阶段(各阶段独立可验证、各自出 plan)

1. **本地 meta 快照**:发消息写 meta + 点历史对话 seed composer 还原(知识库/模型/参数)。
   纯前端,最大价值(直接解决「点历史还原不了状态」),先做。
2. 反馈本地存 + 历史回显。
3. 服务端 `config_snapshot` 字段 + 迁移 + 漫游同步(跨设备)。
4. 上下文继续激活缺口核对/修复(很可能阶段1顺带)。
后续:反馈服务端漫游、视频/数字人统一历史(本设计范围外)。
阶段1 完成即解决核心痛点(同设备点历史完整还原)。

## 风险

- 中等:跨前后端。靠「复用现成 meta 列 + scoped store seed 机制 + 服务端加列 nullable 兼容
  + 分阶段(阶段1 纯前端先落地)」控制。
- 版本号一律走 scripts/bump-version.py。
