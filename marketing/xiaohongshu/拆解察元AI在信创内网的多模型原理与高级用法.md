# 拆解察元AI在信创内网的多模型原理与高级用法

在信创内网用了察元两个多月，从架构角度理解了它怎么做多模型对接的，分享给有技术背景的朋友。

首先明确一个架构事实：察元是Tauri壳 + 内嵌Python FastAPI后端。启动时会在127.0.0.1:62581开一个本地HTTP服务器。这个后端干什么呢？
1. 跑本地模型推理（chat、embedding、asr、ocr、tts都有各自的推理引擎）
2. 路由外部API调用（识别用户选的模型，转换协议，代理请求）

这就涉及到openclaw和Hermes这两个技术栈。openclaw定义了一种统一的"消息格式"和"调用标准"，不管后面是claude-3还是gpt-4o还是本地llama，都用同样的JSON结构表示。Hermes是基于这个标准的一个开源路由框架，能自动识别不同厂商的API格式，做转换和优化。

察元内置了Hermes的能力，所以你在前端选一个模型后，后端会自动：
1. 检查是本地模型还是外部模型
2. 如果是外部，根据模型ID识别是哪家服务商（比如通过base_url判断是内部还是公网）
3. 把用户的prompt转换成那家服务商的格式（OpenAI格式、DashScope格式、内部Hermes格式等）
4. 发请求、拿结果、转换回来、返给前端

对内网部署的优势是什么？
1. **零跨域延迟**：内部模型服务在同一个局域网，不用经过公网，response time快。
2. **格式兼容**：你的内部LLM如果支持OpenAI或Hermes协议，察元直接无缝接。
3. **embedding本地化**：你可以用中文embedding模型（比如bge-m3），建索引时不需要发送文本到任何云端。

高级用法场景：我们做过一个合同风险分析的pipeline。
1. 上传100份合同PDF到知识库。
2. 用本地embedding模型（bge-m3）对所有文本分段embedding，存到CHAYUAN_ROOT的SQLite向量库。
3. 用户输入查询"这些合同里有哪些高风险的违约条款"。
4. 后端在本地向量库做ANN搜索（最近邻搜索，只需要计算相似度）。
5. 把top-k个相似段落喂给内部LLM做深度分析。
6. 用户拿到的是一份结构化的风险报告，每个风险都带原文位置可点开。

为什么这个流程效果好？
- embedding在本地，不泄露客户信息的内容
- 向量搜索很快，filtering也在本地
- 分析用的是我们公司自己的LLM，模型weights不出企业网
- 整个pipeline都是deterministic的，可复现可审计

对比用公网ChatGPT或Claude做同样的事：
- 你必须把合同内容上传到美国的服务器
- 公司安全部门肯定投反对票
- 成本按token计费，100份合同×分析可能贵得离谱

所以信创内网用察元，不是"将就用"，是"该这样用"。架构决定了它特别适合这个场景。

最后一个细节：数据持久化。所有的embedding索引、对话历史都存在CHAYUAN_ROOT下的SQLite数据库里。这意味着：
- 你可以随时备份整个数据目录
- 可以写脚本查询数据库（SELECT语句查对话、查embedding）
- 可以离线分析（关掉察元，用sqlite3命令行工具查）
- 换电脑时可以直接迁移（复制数据目录到新电脑，指向同样的CHAYUAN_ROOT位置）

这种"数据可触及"的设计，对企业级应用特别重要。
